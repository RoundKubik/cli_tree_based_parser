# Documentation corpus extraction

This offline tool extracts per-format annotations with Codex CLI and builds a
synthetic device catalog from another documentation corpus. It does not change
the parser, evaluate predicates, or infer real device behavior.

Install the optional dependency and make the project available to Python:

```bash
python -m pip install -e '.[corpus]'
```

Run commands below from the repository root. Codex CLI must be installed and
authenticated. The extraction model is explicit; the example uses the inexpensive
model available in the development environment, not a guarantee of availability
on another account. Supply `--codex /absolute/path/to/codex` if it is not on PATH.

## CloudEngine pilot and full corpus

```bash
python -m scripts.corpus_pipeline extract \
  --corpus /path/to/cloudengine/cmd_corpus \
  --output-dir data/generated/cloudengine \
  --model-type 'CloudEngine 9800/8800/6800' \
  --software-version v300r024c00 \
  --model gpt-5.6-terra \
  --pilot 30 --workers 3
```

The pilot selects ACL, BGP, interface and related commands first. Inspect the
results, then run the **same command without `--pilot 30`** to process every page.
Formats whose first keyword is `display` (case-insensitive) are excluded **before
any LLM call**. Pages containing only these formats are skipped entirely. A mixed
page keeps its configuration variants and their original `format_index` values.
The report counts skipped pages and formats across the source corpus. The same
filter applies to the NE40E mock; `display-name` is not the `display` keyword.

There are two phases. First, every received JSON response is saved in `pages/`
exactly as returned by the agent, including transition names and evidence. Only
after collection finishes does the tool validate the saved responses and assemble
catalogs. Validation errors do not delete, rewrite, or automatically regenerate
the original answers. Even rejected annotations remain available for inspection.

Completed pages are reusable. The cache key includes source text, related command
formats, prompt, schema and model. Changing these invalidates the corresponding
cached result. `--timeout` limits one model call (default 300 seconds). Errors
remain in the report and do not silently become empty annotations. Exit status 1
indicates failed pages/formats; `pages_validation_failed` distinguishes rejected
responses from failed extraction. Uncertain facts are reported separately.

For a focused prompt experiment, replace `--pilot 30` with
`--page 2.4.3.34_port_trunk_allow-pass_vlan.json` using the exact source filename
(including case), and use a separate output directory. `--page` can be repeated.
For pages that do not belong to system view, set `--entry-view` to one of their
source parent views so the isolated grouped sample has a valid entry reference.

For the fixed CloudEngine sample, replace `--pilot 30` with:

```bash
--selection scripts/corpus_pipeline/samples/cloudengine.json --workers 4 --timeout 180
```

The selection contains 49 source pages and 129 non-display formats, including
undo variants, parameterless commands, composite identifiers and repetition.
It covers related entry and child commands for access control, interfaces, VLANs,
routing, route policies, VPNs and the gRPC IPv4/IPv6 server entry chains. It is a development sample, not a complete or
manually verified hierarchy. Use a new output directory when comparing prompts
so that both sets of original model answers remain available.

Codex runs in a temporary directory with a read-only tool sandbox, ephemeral
sessions, low reasoning effort, and the supplied JSON Schema. The prompt asks it
to use only the provided page, without tools. The runner ignores user project
configuration to avoid attaching unrelated MCP tools or repository instructions.
It still uses the normal Codex authentication. The adapter uses the documented
[`codex exec --output-schema` interface](https://learn.chatgpt.com/docs/non-interactive-mode).

Outputs:

- `documentation_flat.json`: one record per original page/format occurrence.
- `documentation_grouped.json`: the same annotations grouped by source view.
- `report.json`: counts, failures, unresolved facts, and source locations.
- `pages/`: complete original model responses, before validation, for inspection.
- `response.schema.json`: the agent response contract for that run.

Both catalogs retain vendor, device, model and software version. The original
`format` strings and `parent_views` are assigned by Python, never generated by the
model. Multiple formats on the same page keep independent annotations. Identical
formats from different pages are not assumed to carry identical semantics.

The source URL comes from the existing corpus manifest. When the source is a PDF,
the report retains its section and physical page numbers; it does not invent a
separate web URL for each command. `sources.command_start` and `command_count`
locate a page's records in the flat catalog; `format_indices` retains their original
indices within `CLIs`, including gaps left by excluded display variants.

## Per-format annotations

### Portable prompt

`prompt.txt` and `response.schema.json` define the extraction contract independently
of the runner. The prompt is organized as four explicit checks: parameter types,
view transitions, entity effects and command requirements. It contains no
command-specific expected answers. Its intended external target is Qwen3.8-27B;
local extraction runs use Terra through Codex CLI. Those runs do not measure
Qwen's accuracy or performance.

In another pipeline, send `prompt.txt` as the instructions and the JSON produced
by `page_input` as input data. Supply `response.schema.json` through the backend's
structured-output facility, or include it with the instructions if that facility
is unavailable. Preserve the complete response before applying the same checks.
No Codex tools, repository access or model-specific prompt delimiters are needed.

Every supplied parameter name needs a type or a named explanation in `issues`,
including apparent source artifacts such as literals wrapped as placeholders.
Original formats remain unchanged. A command dependency copies its title and
format from the same `related_commands` entry. A composite selector requires
adjacent parameters on one valid syntax path. Facts requiring value
conditions that the schema cannot express remain in issues, not unconditional
semantic rules.

```json
{
  "format": "interface { <interface-name> | <interface-type> <interface-number> }",
  "description": "Create or enter the documented interface.",
  "parent_views": ["System view"],
  "switch_to_view": "Interface view",
  "parameter_types": [
    {"parameter_name": "interface-name", "parameter_type": "string"},
    {"parameter_name": "interface-type", "parameter_type": "string"},
    {"parameter_name": "interface-number", "parameter_type": "string"}
  ],
  "creates": [
    {"kind": "entity", "parameter_name": "interface-name", "entity_type": "interface"},
    {"kind": "entity", "parameter_comb": ["interface-type", "interface-number"], "entity_type": "interface"}
  ],
  "requires": []
}
```

This example illustrates the contract, not a claim about every Huawei interface
command. The source must establish the effects and target.

An entity selects either one parameter or an ordered combination of placeholders
written directly next to each other in the original format, separated only by
whitespace: `<first> <second>`. It applies only when all selected parameters are present.
Parameterless entities are allowed when documented; their rule has only `kind`
and `entity_type`. The combination validator checks the literal placeholder
sequence. Keywords, grouping boundaries and repetition operators cannot be
crossed, even when a runtime path could make the values adjacent.

A command requirement has `kind: command`, `name`, `format`, and `context`:

```json
{
  "kind": "command",
  "name": "feature enable",
  "format": "feature enable",
  "context": "unresolved"
}
```

`name` is the documented command title; `format` must occur under that title in the
source corpus. `system` means the root configuration context, `current` means the
same contextual instance, and `unresolved` preserves a known requirement with an
unknown scope. A preceding example command is not by itself a prerequisite.
Entity references are also extracted from `FuncDef` and `ParaDef`, including undo
operations. They do not require an explicit Prerequisites sentence. Range endpoints
such as `vlan-id1` and `vlan-id2` produce independent entity rules; they are not a
composite identifier. Ordinary numeric attributes are not entity references.
Unrepresentable conditional requirements and references without an established
format remain in the issue report, never as invented unconditional rules.

Types use parser built-in IDs: `string`, `integer`, `ipv4-address`, `ipv6-address`,
`text`, `hex`, `mac`, `ipv6-prefix`, `passwordex`, `date-slash`, `date-iso`,
`month-day`, `date-us`, `datetime-slash`, `time-seconds`, and `time`.
Unknown/union types use `unknown` with an issue, not a guessed `string`. The matcher
accepts the same type set; `text` compares as `string`. `unknown` preserves the format
and possible bindings, but cannot prove hierarchy. The runtime parser also uses known
`parameter_types` to validate named values without imposing undocumented numeric
ranges or lengths. `unknown` keeps the unvalidated named behavior; `text` reads the
remainder of the line. See the [parser contract](../../docs/reference/automaton-parser.md).

Assembly completes omitted names with `unknown`, except when the source explicitly
declares a string. Quoted strings are still strings; supporting their runtime reader
is a separate concern. Existing known annotations are preserved. Raw model answers
and issues stay unchanged, and `report.json` lists these programmatic `type_changes`.

For previously generated catalogs, apply the same completion in a separate directory:

```bash
python -m scripts.corpus_pipeline repair-types \
  --input-dir data/generated/cloudengine_terra_grpc \
  --hierarchy-dir data/generated/cloudengine_hierarchy_grpc \
  --corpus /path/to/cloudengine/cmd_corpus \
  --output-dir data/generated/cloudengine_types_repaired
```

This writes `documentation_flat.json`, `documentation_grouped.json`, and
`type_report.json`, retaining every format, view position, transition and semantic
annotation. Source indices are checked before copying annotations. Unknown types
remain listed for review; accepting the catalog does not mean all types are known.

## Transitions and uncertainty

In the extraction result `switch_to_view` is a string or null. Null with no issue
means no transition. Null with a `switch_to_view` issue means the destination is
unknown or conflicting. Read the flat catalog together with its report.

During grouped assembly, spelling-only aliases (case and whitespace) are resolved
against `ParentView` names. No semantic alias such as `gRPC IPv4 server view` →
`GRPC server view` is guessed. A generic `ACL view` is never narrowed to a specific
ACL view. A known target remains a string even if its command group has not been
identified. For example, `switch_to_view: "ACL view"` is retained; a missing
`ACL view` group is reported as `view_membership`, counted in
`targets_without_groups`. This is a hierarchy-linking problem, not an unknown
transition. Such an extraction catalog still needs hierarchy normalization before
it can satisfy the runtime parser's strict group-reference checks.

Only an actually unknown/conflicting transition uses the parser's existing
representation in the grouped export:

```json
{"switch_to_view": {"status": "unresolved"}}
```

This lets an unknown child block use the parser's existing fallback. It does not
claim hierarchy recovery. Missing targets do not become empty groups merely to
pass reference validation. `All views` is retained literally; expanding it into
runtime availability and semantic group merging are separate hierarchy work.
Pilot output can lack target groups whose pages have not been selected yet.

Report counts measure processing readiness, not semantic accuracy. Source grammar
errors, model-call failures, unresolved types, dependencies and targets remain
visible. No manually verified reference corpus is claimed.

### What to inspect or send for correction

| Stage | Report entries | Review action |
|---|---|---|
| Extraction | `report.json`: `errors`, `issues`, `type_changes`, `sources` | Open the saved response in `pages/` and its source page; inspect the indicated `format_index` and field |
| Type completion | `type_report.json`: `unknown_types`, `changes` | Check unsupported representations and quoted evidence; do not substitute a guessed type just to pass validation |
| Documentation hierarchy | `hierarchy_report.json`: `transitions`, `conflicting_formats`, `aggregates`, `reachability`, `evidence_errors` | Inspect unknown/ambiguous/missing targets, conflicting effects, incomplete groups and unreachable views |
| Device matching | `report.json`, `mapping.json`, `hierarchy_report.json` from the experiment runner | Separate unmatched formats, unfinished comparisons, partial bindings and unresolved view correspondence |

Extraction validation checks the schema, parameter references, adjacent composite
selectors, dependency formats and transition quotations. It does not independently
verify all `creates`/`requires` assertions or guarantee semantic consistency across
pages. There is no automatic correction-agent queue. The recorded source location,
original response, reported issue and relevant documentation can be supplied to a
reviewer or an agent without rerunning the whole corpus. Keep the original response
and validate a corrected copy before rebuilding derived catalogs.

## Reuse with another LLM pipeline

The reusable assets are [prompt.txt](prompt.txt) and
[response.schema.json](response.schema.json). Send the prompt as the extraction
instruction and a page-input JSON as data. Request a response matching the schema.
There is no Codex-specific reasoning or tool requirement in the prompt.
Its extraction rules are general: view names follow source descriptions, entity
references follow documented parameter roles, and composite selectors identify
one entity within a branch. It contains no command-specific expected answers.
The concrete examples in this guide are not included in the LLM instruction.

The response uses `format_index`, so a model never needs to copy long command
formats. The caller joins the result to the input record with the same
`format_index` (not its array position after filtering) and copies
the source `parent_views`. `switch_evidence` and `issues` stay in the original
responses; the catalogs contain the requested annotations from responses that
passed validation. Schema validation alone cannot
check parameter membership or prove factual correctness.

To produce an actual page-input example or validate an external response:

```python
from pathlib import Path
from scripts.corpus_pipeline.source import Corpus, write_json
from scripts.corpus_pipeline.extraction import page_input
from scripts.corpus_pipeline.contract import validate_response

corpus = Corpus(Path("/path/to/cloudengine/cmd_corpus"))
page = corpus.pages["2.5.10.8_acl_number.json"]
write_json(Path("/tmp/acl.input.json"), page_input(page, corpus))
# annotations = validate_response(llm_response, page, corpus)
```

The checked-in schema is generated from `contract.RESPONSE_SCHEMA`; a regression
test checks that both remain identical.

## NE40E mock device catalog

```bash
python -m scripts.corpus_pipeline mock-device \
  --corpus /path/to/ne40e/cmd_corpus \
  --output-dir data/generated/ne40e_mock \
  --model-type 'NE40E (documentation-derived mock)' \
  --software-version v800r024c00spc500
```

This processes every non-display format without LLM calls. It preserves syntax and views,
replacing only parameter AST spans with parser-supported device declarations.
Repeat operators such as `&<1-10>` are never treated as named parameters.
Explicit representations in `ParaDef` select types, with simple decimal ranges
retained when available. Other bounds are deliberately synthetic. Parameters
whose type cannot be extracted keep their original named placeholder and appear in
`unknown_types`. Scalar integer ranges are not inferred from compound values such
as AS numbers with dotted notation or number/address pairs. IPv6 prefixes use
`X:X::X:X/M`, including when the source describes them as strings. This heuristic
is for a mock fixture only, not trusted semantic/type extraction. Unknown named
placeholders accept a token at runtime, but cannot prove hierarchy in the matcher.

Outputs are `device_flat.json`, `device_grouped.json`, and `report.json`. Invalid
source patterns are excluded from runnable catalogs and enumerated in the report.
The grouped mock has **no recovered transitions** and uses documentation view
names, not actual device view IDs. Use its flat version for immediate parsing;
the grouped version is input for subsequent hierarchy-recovery experiments.

## Recover documentation hierarchy

Run all recovery stages against the completed extraction and the original pages:

```bash
python -m scripts.corpus_pipeline recover-hierarchy \
  --input-dir data/generated/cloudengine_terra_complete \
  --corpus /path/to/cloudengine/cmd_corpus \
  --output-dir data/generated/cloudengine_hierarchy \
  --model gpt-5.6-terra --workers 4
```

Add `--codex /path/to/codex` when needed. `--entry-view` defaults to `System view`.
`--global-view` can be repeated to identify shared scopes; its default is
`All views`. A separate output directory is required. Original annotations,
formats, parameter types, entity semantics and parent view names are retained.
Only resolved transition references and explicit unresolved markers change.

The command performs these stages:

1. Group every source record by all of its `parent_views`.
2. Resolve exact target names, then unique case/whitespace-normalized names.
   Exact names win; normalization collisions stay ambiguous. Original group keys
   are never renamed or merged merely because they normalize alike.
3. Consult source documentation for unmatched targets and uncertain transitions.
   Terra receives the entry page and candidate supporting pages, including CLI
   examples and source cross-references. Explicit links to the entry page take
   precedence over short unrelated descriptions. Up to twelve candidate scopes
   and three complete examples per page are supplied; the original example count
   remains visible. Lexical overlap
   ranks retrieval only; it cannot establish a relationship. There are no manual
   view correspondence tables or command-specific alias rules.
4. Save complete model answers before checking their structure, quoted passages,
   target scopes and member provenance. Rejected evidence does not establish a
   link. Changed requests archive previous answers under `evidence/history/`.
5. Build the grouped catalog, materialize shared commands, check references and
   compute reachability. Known exits are counted separately from child entries.

Outputs:

- `documentation_grouped.json`: the catalog accepted by the existing parser.
- `hierarchy_report.json`: transition decisions, source locations, aggregate
  membership, uncertain cases, conflicts and reachability.
- `evidence/`: portable hierarchy prompt/schema, requests, original answers and
  archived earlier answers. The numeric evidence key refers to the first source
  command involved; it is not a new command ID in the catalog.

Transition statuses in the report:

| Status | Meaning |
| --- | --- |
| `resolved` | One target group is linked by exact spelling, normalization or documented alias evidence |
| `grouped` | A documented generic destination contains available member commands |
| `unknown` | No destination or supported alternatives were established |
| `ambiguous` | Several interpretations remain; candidate lists may be incomplete |
| `missing` | A target is known but no usable group link was established |
| `exit_parent` | The command leaves the current context for its parent/previous view |
| `exit_view` | The command exits to a fixed named view |

For a documented aggregate, original member groups stay in the catalog and the
new generic group contains their source records, deduplicated by source occurrence.
This is a deliberately broader command scope, not a claim that members are equal
or that a parameter-specific member has been determined. `exhaustive: false` and
`members_without_commands` expose incomplete family coverage. No empty group is
invented simply to satisfy a missing reference.

`origins[view][index]` identifies the original flat command index, including
records copied into aggregates and shared scopes. Record formats remain unchanged,
so parameter source spans are preserved. Source annotation order is stable within
original groups; appended shared commands do not renumber their existing entries.

`All views` remains a source group, but is excluded as a concrete graph node.
Shared records are copied into actual groups because the parser has no global
inheritance mechanism. For large catalogs this intentionally increases output
size; `shared_copies` reports that cost.
The grouped output also declares these scopes in `shared_views` for the optional
hierarchy mode. The default system/non-system matcher ignores that field and uses
only the original group membership and `entry_view`.

`quit`-like parent exits keep an unresolved runtime transition because the current
parser has no stack-pop transition field. Fixed exits retain their known target.
The report describes both effects, but the parser still follows configuration
indentation, not an interactive command session. Neither exit contributes to
`entered_views`; fixed exits contribute to `reachable_with_fixed_exits`.

`members_covered_by_aggregates` is separate from concrete `entered_views`.
`unreachable_views` means no path was established in this selected corpus; it does
not mean the view is invalid or unreachable on the device. Missing entry formats,
uncertain transitions and a limited sample can all leave such gaps.

Source quotations establish provenance, not a mathematical proof of the model's
interpretation. Exact/normalized links and documented aliases are counted
separately. Review `evidence/` for important semantic decisions. The extractor's
remaining type/semantic issues are unchanged; the matcher still needs its separate
annotation compatibility checks. This command neither modifies the parser nor
performs device hierarchy recovery or device-to-documentation matching.

## Reproduce parser and matcher experiments

The same four configuration fixtures exercise ACL/gRPC, BGP families, interface
fallback and VPN families. They are synthetic inputs, not device validation.

```bash
python -m scripts.corpus_pipeline.experiment parser \
  --catalog data/generated/cloudengine_hierarchy_grpc/documentation_grouped.json \
  --output-dir data/generated/pipeline_checks/documentation

python -m scripts.corpus_pipeline mock-device \
  --corpus /path/to/ne40e/cmd_corpus \
  --output-dir data/generated/ne40e_mock \
  --global-view "All views" \
  --model-type NE40E --software-version v800r024c00spc500

python -m scripts.corpus_pipeline.experiment parser \
  --catalog data/generated/ne40e_mock/device_flat.json \
  --output-dir data/generated/pipeline_checks/ne40e_flat

python -m scripts.corpus_pipeline.experiment matcher \
  --device data/generated/ne40e_mock/device_grouped.json \
  --documentation data/generated/cloudengine_types_repaired/documentation_grouped.json \
  --output-dir data/generated/pipeline_checks/matcher
```

The mock excludes `display` variants before conversion. Invalid source grammar is
reported, with the remaining valid formats still written; an exit code of 1 makes
these omissions visible. Composite values whose component ranges resemble integer
constraints keep their named placeholders; the converter cannot infer a scalar
validator for the whole token. This is still a synthetic, partly heuristic conversion.
The optional repeatable `--global-view` argument declares shared scopes in the
grouped mock only. It does not infer a scope from its spelling, add runtime copies
or change the flat output. Each declared scope must exist in the source corpus.

The matcher experiment defaults to system/non-system scopes over the unchanged
input catalogs. It skips hierarchy recovery; `runtime_catalog.json` is an unchanged
copy of the target catalog. Use `--context-mode hierarchy` to run the previous
hierarchy experiment and produce `hierarchy_report.json`. The parser experiment
accepts the same option and otherwise selects its scope by indentation.

The matcher experiment first validates supplied annotations. Missing annotations
are accepted as unknown types. Malformed entries, unsupported types, duplicate names and references to
absent parameters still fail validation. If any fail, it writes
`input_validation.json` and stops. An
explicit `--compatible-only` run selects a separate documentation subset; it never
changes types or fills missing annotations. `documentation_selection.json` records
every excluded occurrence and maps the selected view/index back to the original.
All mapping references then address `documentation_compatible.json`.

Successful matching writes `mapping.json` with two-space indentation, all bindings and
scope automata, plus `runtime_catalog.json`. `hierarchy_report.json` distinguishes
resolved targets, multiple fully covering targets, partial coverage, unknown
coverage (types or limits), and missing evidence. It also lists unknown parameter
types and unresolved documentation switches without duplicating slot bindings.
Use the runtime catalog in another `parser`
experiment. Do not use the raw grouped mock as a recovered hierarchy: it has no
known transitions. To compile its full grouped contents with flat lookup, pass
`--flat` explicitly.

`report.json` counts device-format occurrences by `matched`, `partial`, `unmatched`
and `unknown`, as well as pair stages/relations, bindings and unresolved transitions.
Only categories present in a run appear. An unmatched format is not a processing
error, and `unknown` is not proof of absence. A matched device can still have some
unfinished pairs, so inspect pair relations as well. These files are written by the
experiment runner; the core matcher API returns in-memory results.

To inspect individual commands without duplicating mapping data:

```python
for pattern_id, command in mapping["devices"].items():
    if command["status"] != "matched" or any(
        pair["status"] == "unknown" for pair in command["mappings"]
    ):
        print(
            pattern_id, command["source"], command["status"], command["device_format"]
        )
        for pair in command["mappings"]:
            print(pair["document_id"], pair["stage"], pair["status"])
```

Each experiment writes `report.json` with elapsed time and peak resident memory.
Parser cases retain the complete parse results, context issues and slot IDs.
Recognition counts and known-context counts are separate. A completed experiment
is not a claim that every line was recognized or every context recovered.
On Linux, experiments have explicit process limits (`--seconds`, default 300;
`--memory-mb`, default 1536). A limit failure is recorded as incomplete, not as
absence of matching formats. Source catalogs and production parser/matcher APIs
are unchanged by the experiment runner.

The parser experiment also reports `unresolved`: recognized commands returned as
`UnresolvedCommand` because their context is unconfirmed. They retain `primary_match`
and alternatives; they do not count as known-context successes or syntax errors.

The local repaired-corpus run is summarized in
`data/generated/pipeline_checks/type_and_hierarchy_report.json`. Its matcher output
is under `pipeline_checks/matcher_repaired/`, including `integrity.json` checks of
catalog positions, all saved bindings, scope graph references, and runtime slot IDs.
The reference has 129 original formats (489 grouped occurrences), of which 21 still
contain unknown types. All are retained. The full NE40E mock has 89,065 grouped
occurrences; 11 malformed source formats are reported separately by its converter.
The fixtures recognize all 31 commands, with known context for 26 documentation
lines and 18 device lines. These results expose remaining gaps; they do not imply
complete hierarchy recovery or validated command semantics.
