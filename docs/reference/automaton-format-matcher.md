# Сопоставление форматов для парсера на автомате

`vrp_format_matcher` — отдельный пакет для `vrp_parser_automaton`. Он сравнивает
форматы документации и устройства, подготавливает соответствия параметров,
а затем применяет метаданные к результату разбора конкретной команды.
Импортов `vrp_parser` и зависимости от старого модуля metadata нет.

## Сравнение двух форматов

```python
from vrp_format_matcher import FormatMatcher

comparison = FormatMatcher().compare(
    "command { <a> | <b> to <c> }",
    "command INTEGER<1-100> [ to INTEGER<1-100> ]",
)
print(comparison.relation)  # equivalent
print(comparison.common_example)
```

Документальные параметры обозначаются `<name>`. Литералы сравниваются без
учёта ASCII-регистра. Все параметры представлены одним структурным символом
`P`, независимо от имени, типа и диапазона. Литерал и параметр — разные
символы. Даже `TEXT` считается одним параметром, хотя реальное значение может
содержать пробелы. Это сравнение структурных языков, а не множеств всех строк,
проходящих конкретные валидаторы устройства.

| `relation` | Значение |
|---|---|
| `equivalent` | Одинаковые структурные языки |
| `document_subset` | Документация описывает строгое подмножество команд устройства |
| `device_subset` | Устройство описывает строгое подмножество документальных команд |
| `overlap` | Общие команды есть, и у каждой стороны есть собственные |
| `prefix_only` | Общих полных команд нет; есть диагностический общий префикс |
| `disjoint` | Нет общих полных команд и непустого общего префикса |
| `unknown` | Подготовка не завершилась в пределах бюджета |

`structurally_identical` сравнивает исходную структуру без имён и типов
параметров, с сохранением порядка веток. Перестановка веток может дать
`equivalent` при `structurally_identical=False`.

`common_example`, `document_only_example`, `device_only_example` содержат
найденные свидетельства. `<PARAM>` в них обозначает позицию параметра.
`common_prefix` — пример префикса, не обещание найти самый длинный.
Для `prefix_only` автоматического переноса метаданных нет.

## Подготовка и runtime

```python
from pathlib import Path
from vrp_parser_automaton import CommandLineParser, ParsedCommand
from vrp_format_matcher import FormatMatcher, PreparedMapping

parser = CommandLineParser({
    "commands": ["command INTEGER<1-100> [ to INTEGER<1-100> ]"]
})
prepared = FormatMatcher().compile(parser, [{
    "id": "range-command",
    "format": "command { <a> | <b> to <c> }",
    "requires": [{
        "when": "always",
        "condition": "parameter_name",
        "parameter_name": "b",
        "entity_type": "vlan",
    }],
}])

Path("/tmp/format-mapping.json").write_text(prepared.to_json(), encoding="utf-8")
runtime = PreparedMapping.from_json(
    Path("/tmp/format-mapping.json").read_text(encoding="utf-8")
)

line = parser.parse("command 10 to 20")
if isinstance(line, ParsedCommand):
    report = runtime.evaluate(line)
    print(report.to_dict())
```

`compile` принимает уже созданный парсер устройства и массив документальных
записей. Для каждой пары-кандидата возвращается `PreparedPair`. `creates` и `requires`
необязательны: без них можно сравнивать форматы и получать привязки. Если правил
нет, статус эффектов может быть `inactive`, хотя привязки успешно получены.
Сами привязки находятся в `application.alternatives[*].bindings`.

В примере первый параметр устройства соответствует `a` для `command 10`
и `b` для `command 10 to 20`. Подготовленное соответствие зависит от полного
пути, поэтому не сводится к безусловной таблице номеров параметров.

Каждый `ParameterBinding` содержит исходные слоты документации и устройства,
имя документационного параметра и уже проверенное значение из парсера.
Координаты вложенных повторений сохраняются. Несколько возможных привязок
остаются в `alternatives`; истинность предиката не выбирает одну из них.
`binding_status` показывает `unique`, `ambiguous` или `unavailable`.

`rules` содержит согласованный результат каждого правила. Общая зависимость
может оказаться однозначной даже при разных привязках. Статусы применения:
`applied`, `inactive`, `ambiguous`, `not_applicable`, `unknown`.

Имена `MetadataCompiler` и `PreparedMetadata` доступны как синонимы
`FormatMatcher` и `PreparedMapping`.

## Большие каталоги и индекс кандидатов

По умолчанию `compile` строит префиксное дерево форматов устройства и выбирает
кандидатов через него. Полного перебора `число документов × число команд` нет.
Индекс использует до восьми начальных структурных токенов, поэтому различает
не только `display` и `undo`, но и следующие за ними ключевые слова.
Параметры представлены символом `P`, как и при сравнении языков.

`PrefixCover` читает AST: учитывает альтернативы и пропуск необязательных
частей, а для наборов и повторений ограничивается возможным началом первой
ветки или итерации. Сохраняется не более 64 префиксов на промежуточный результат.
При превышении ширины они заменяются общим префиксом; при достижении глубины
продолжение считается произвольным. Это консервативный фильтр: он может оставить
лишние пары, но не исключает пару с общей полной командой.

`prepared.pairs` теперь **не является полной матрицей сравнения**. Исключённые
пары не сохраняются в JSON и не создают runtime-применений метаданных. Пустой
список означает, что индекс не нашёл кандидатов. Наличие пары ещё не доказывает
пересечение: окончательный результат находится в `pair.comparison`.

Для диагностики конкретной пары используйте `compare(doc, device)`: он всегда
проводит сравнение, включая `prefix_only` и `disjoint`. Для небольшого каталога
можно явно вызвать `compile(parser, documents, exhaustive=True)`, чтобы получить
прежнюю полную матрицу. Для каталогов в тысячи записей этот режим не подходит.

Прогресс можно получать через `compile(..., on_progress=callback)`. Callback
принимает `PreparationProgress` с полями `documents_done`, `documents_total`,
`pairs_prepared`. События приходят после построения индекса и после каждого
документа, включая документы без кандидатов. Внутри одного долгого сравнения
событий нет.

Для выбранных кандидатов переиспользуются ε-фронтиры документального автомата.
После расхождения языков обход одностороннего продолжения прекращается, как
только найдено соответствующее свидетельство различия. Общие пути при этом
продолжают проверяться.

## Как используется автомат парсера

1. Инструкции устройства берутся из `parser.automaton`. Они не строятся
   повторно для каждой документальной записи. Для пары выделяется достижимый
   фрагмент нужного шаблона.
2. Документальная строка разбирается тем же `PatternParser` с распознавателем
   именованных параметров. Её AST компилируется тем же `AutomatonBuilder`.
3. Для равных канонических структур язык признаётся эквивалентным без обхода
   всех конфигураций. Если нормализованный разбор однозначен, к готовым
   инструкциям устройства добавляются прямые аннотации параметров.
4. В общем случае выполняется ленивое сравнение множеств конфигураций и
   строится пересечение по потребляющим переходам. Независимые ε-переходы
   не перемножаются. Ветви, не ведущие к полному совпадению, удаляются.
5. Runtime исполняет уже подготовленные инструкции или граф пересечения.
   Форматы не разбираются и не сопоставляются заново.

`runtime/program.py` вызывает `vrp_parser_automaton.runtime.execution.ControlFlow`.
В матчере нет второй реализации семантики выбора, масок наборов или счётчиков
повторений. Структурный адаптер убирает только историю, влияющую на представление
результата, и сохраняет регистры, необходимые для распознавания. На переходах
остаются аннотации исходных параметров.

При runtime-анализе из `ParsedCommand` восстанавливаются атомы по spans значений.
Дополнительный проход по подготовленному распознавателю сохраняет привязки,
которые публичный парсер мог объединить как равнозначные разборы. Например,
`[ PARAM ] [ PARAM ]` с одним значением требует учёта обоих исходных слотов.

## Метаданные и предикаты

Записи `requires` и `creates` поддерживают цели `condition: parameter_name`
с `parameter_name` и `condition: command`. Метаданные выдаются вызывающему коду;
наличие VLAN или исполнение зависимой команды модуль не проверяет.

Поле `when`: `"always"`, JSON boolean либо структурированный JSON с `op`:
`exists`, `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `all`, `any`, `not`.

```json
{"op": "exists", "parameter": "upper"}
```

```json
{"op": "gt", "parameter": "vlan-id", "value": 10}
```

Для `all`/`any` используется массив `args`, для `not` — поле `arg`.
Отсутствующие значения не удовлетворяют сравнению. Для правила на параметр
учитываются совместимые координаты повторений. Это небольшой вспомогательный
механизм; сопоставление форматов от предикатов не зависит.

## Структура пакета

```text
vrp_format_matcher/
├── __init__.py       # публичные импорты
├── models.py         # неизменяемые значения и результаты
├── documents/        # входной JSON, имена параметров, проверка правил
├── preparation/      # индекс кандидатов, подготовка пар, аннотации инструкций
├── comparison/       # структура, однозначность, языки и свидетельства
├── runtime/          # адаптер автомата, привязки и применение правил
└── storage/          # JSON подготовленного результата
```

`CompiledPattern` кэширует результат подготовки одного источника, включая
причину превышения бюджета. `SourceAlignment` связывает исходные узлы только
после проверки однозначности. `ProgramExecution` отделяет ε-обход от истории
привязок в `BindingSearch`. `MetadataRules` отвечает за применение правил,
а `ProgramStorage` — за сериализацию инструкций.

## Ограничения и артефакты

Компактное представление не устраняет худший случай экспоненциального сравнения
разных или неоднозначных языков. `MappingLimits` сохраняет отдельные бюджеты
инструкций, сравнения, пересечения и runtime-конфигураций; значения по умолчанию
20 000. Бюджеты обходов также ограничивают одно ε-замыкание. Превышение даёт
`unknown`, а не ложный `disjoint` и не частичные привязки.

Для одинаковых однозначных наборов из 24 переставленных веток с параметрами
достаточно 53 инструкций парсера. Повтор `&<1-100000>` в ручном примере занимает
6 инструкций. Однако пересечение двух существенно разных широких наборов
может превысить бюджет.

Стоимость подготовки зависит от количества кандидатов после индексирования.
Если множество форматов имеет одинаковые первые восемь токенов или очень широкое
начало, индекс может сохранить много пар. Он не гарантирует линейного времени
для произвольных каталогов и не упрощает само пересечение сложных языков.

Артефакт имеет `kind: "vrp-format-matcher"`, `version: 1`. Он хранит связанные
инструкции, аннотации и правила и загружается без парсинга документации.
Артефакты старого `vrp_parser.metadata` имеют другое представление и не
поддерживаются. Артефакты следует считать доверенными данными собственной
подготовки. После изменения форматов или правил их нужно пересобрать.
Пользовательские валидаторы в JSON не сохраняются: парсер устройства при
исполнении должен использовать совместимый реестр.

## Ручная проверка

```bash
python3.13 manual_format_matcher_test.py --case vlan
python3.13 manual_format_matcher_test.py --case conditional
python3.13 manual_format_matcher_test.py --case ambiguous
python3.13 manual_format_matcher_test.py --case overlap
python3.13 manual_format_matcher_test.py --case prefix
python3.13 manual_format_matcher_test.py --case wide-set
python3.13 manual_format_matcher_test.py --case wide-optional-set
python3.13 manual_format_matcher_test.py --case large-repeat
```

Свою пару каталогов можно передать через `--patterns device.json`
и `--documents documentation.json`; строки — через повторяемый `--line`.
Документальный JSON — массив записей с полем `format`.
При работе с файлами скрипт использует индекс и пишет прогресс в stderr каждые
100 документов и в конце. `--exhaustive` включает полную матрицу только для
небольших диагностических запусков. Встроенные примеры `--case` сравниваются
полностью, чтобы пример `prefix` показывал диагностическое расхождение.

```bash
python3.13 manual_format_matcher_test.py --case wide-set --save /tmp/prepared-formats.json
python3.13 manual_format_matcher_test.py --load /tmp/prepared-formats.json \
  --line 'command option23 24 option0 1'
```

Скрипт показывает отношение языков, стратегию, размер подготовленного
представления, возможные соответствия и конкретные привязки. `--json`
добавляет полные данные runtime-результата.
