# Сопоставление форматов и параметров

`vrp_format_matcher` выполняет офлайн-сопоставление форматов. Результат содержит
отношение форматов, соответствия исходных параметров и статус каждого документа.
Вычисления предикатов, обработки `requires`/`creates`, runtime-метаданных и слоя
артефактов в пакете нет. Дополнительные поля входных документов игнорируются.

## Основной API

Для уже созданного парсера устройства:

```python
from vrp_parser_automaton import CommandLineParser
from vrp_format_matcher import FormatMatcher

parser = CommandLineParser({
    "commands": ["vlan INTEGER<1-4096> [ to INTEGER<1-4096> ]"]
})
result = FormatMatcher().compile(parser, [{
    "id": "vlan-range",
    "format": "vlan <first> [ to <last> ]",
}])

for pair in result.pairs:
    print(pair.document_id, pair.pattern_id, pair.status)
    for binding in pair.bindings:
        print(
            binding.document.name,
            binding.document.slot_id,
            "->",
            binding.device.declaration,
            binding.device.slot_id,
        )
```

Для исходных форматов без создания runtime-парсера:

```python
result = FormatMatcher().compile_formats(
    ["vlan INTEGER<1-4096>"],
    [{"format": "vlan <id>"}],
)
```

Для сравнения документа с документом явно укажите синтаксис целевой стороны:

```python
formats = ["vlan <id>", "clock date-format { YYYY-MM-DD | MM-DD-YYYY }"]
result = FormatMatcher().compile_formats(
    formats,
    [{"format": pattern} for pattern in formats],
    target_syntax="document",
)
```

`target_syntax="document"` распознаёт только параметры в угловых скобках.
В частности, литерал `YYYY-MM-DD` не превращается в тип устройства. Имена
`<8021p-value>`, `<ipv6-address/prefix-length>`, `<yyyy/mm/dd>` поддерживаются.
В режиме `device` распознаются типы устройства, а также именованные `<placeholder>`.
При использовании собственного реестра типов передавайте готовый парсер в `compile`.

## Результат

`PreparedMapping` — обычный неизменяемый объект данных:

- `pairs`: результаты сравнения выбранных пар;
- `documents`: статус каждого документа, включая документы без кандидатов.

У пары доступны:

| Поле | Содержание |
|---|---|
| `document_id`, `document_format` | Документальный источник |
| `pattern_id`, `device_format` | Целевой источник |
| `status` | Отношение языков, также `comparison.relation` |
| `bindings` | Готовые соответствия параметров |
| `binding_mode` | `structural`, `path_dependent` или `unavailable` |
| `comparison` | Отношение, диагностические примеры и причина `unknown` |
| `automaton` | Граф пересечения для разных структур; иначе `None` |

У каждого элемента `bindings` есть `document` и `device`. Они содержат
`slot_id`, `name`, `declaration`, `type_id`. `p:15` означает параметр, начинающийся
с позиции 15 исходного формата, с нуля. Это не порядковый номер. Повторяющееся имя
в разных местах формата имеет разные слоты. При совпадающих структурах параметр
в повторении представлен одним соответствием, а не копией для каждой итерации.

Типизированный параметр устройства обычно имеет `name=None`, но сохраняет
декларацию вроде `INTEGER<1-4096>`. При сравнении документа с документом имена
доступны с обеих сторон.

Статусы пары:

| Статус | Значение |
|---|---|
| `equivalent` | Совпадение структурных языков |
| `document_subset` | Документ описывает часть языка устройства |
| `device_subset` | Устройство описывает часть языка документа |
| `overlap` | Есть общие полные команды и различия с обеих сторон |
| `prefix_only` | Совпадает только начало, полных общих команд нет |
| `disjoint` | Общих полных команд и непустого префикса нет |
| `unknown` | Анализ не завершился в пределах бюджета |

Статус документа — `matched`, `unmatched` или `unknown`; поле `pattern_ids`
перечисляет найденные соответствия. `matched` означает, что найден хотя бы один
подходящий формат, а не доказана уникальность источника. Дубли исходных форматов
сохраняются под отдельными идентификаторами.

## Что сопоставляется

Литералы нормализуются по ASCII-регистру. Все параметры представлены символом
`P`, независимо от имени, типа и диапазона. `P` совпадает только с параметром,
а не с произвольным ключевым словом. Проверки значений остаются задачей парсера.

Для одинаковых канонических AST параметры связываются непосредственно по узлам.
Порядок разных альтернатив не важен. Если несколько альтернатив имеют одинаковую
структуру, они связываются по порядку появления внутри этой структуры. Это
соглашение о соответствии исходных форматов: структура сама по себе не позволяет
восстановить иной семантический порядок неразличимых веток.

Неоднозначность разбора будущей CLI-строки не вызывает раскрытия языков офлайн.
Например, `[ <a> ] [ <b> ]` против двух таких же типизированных позиций даёт
`a -> первая позиция`, `b -> вторая позиция`. Матчер больше не строит все перекрёстные
интерпретации одной конкретной строки.

Если структуры различаются, выполняется сравнение языков и строится пересечение.
В `bindings` попадают только пары параметров на полных общих путях. Для
`binding_mode="path_dependent"` список показывает возможные соответствия;
он не превращает их в безусловную таблицу. Условия пути сохраняются в графе
`automaton`. Для `prefix_only`, `disjoint` и незавершённого анализа соответствия
не выдаются. При `unknown` причина доступна в `comparison.reason`.

## Производительность и режимы

По умолчанию `mode="best"`:

1. Один раз строится индекс по полной канонической структуре целевых AST.
2. Для документа ищутся все цели с такой же структурой.
3. Если они найдены, параметры связываются напрямую. Для этой пары не строятся
   дополнительные автоматы и не выполняется обход языка.
4. Только если такого соответствия нет, используется префиксный индекс и общий
   алгоритм сравнения с кандидатами.

Таким образом, копия корпуса с заменёнными именами или типами параметров не
порождает перебор всех похожих по началу команд. При `compile_formats` автоматы
строятся лениво, только для общего алгоритма.

`mode="all"` также ищет частичные пересечения, даже если уже найдены структурно
равные форматы. Это более дорогой режим с более широким результатом. `best`
намеренно не возвращает все возможные частичные пересечения при наличии точного
структурного соответствия.

`exhaustive=True` отключает оба индекса для диагностики небольших наборов.
`compare(doc, device)` всегда сравнивает указанную пару, включая случаи расхождения.

Префиксный индекс рассматривает до восьми структурных токенов и до 64 вариантов
на промежуточный результат. При превышении бюджета фильтр расширяет кандидатов,
не отбрасывая возможное пересечение. Общий алгоритм использует ленивые множества
конфигураций и переходы основного автомата парсера. Он не создаёт полный DFA заранее.

`MappingLimits` ограничивает инструкции, состояния сравнения, пересечения и
число операций анализа (`analysis_steps`, по умолчанию 200 000 на пару). Последний
бюджет учитывает и ε-обходы, и обработку переходов, а не только сохранённые состояния.
Сложное сравнение возвращает `unknown` вместо неограниченной работы или ложного
отсутствия совпадения. Это бюджет операций, а не таймер.

Прогресс доступен через `on_progress(event)`: `documents_done`, `documents_total`,
`pairs_prepared`. Событие приходит после каждого документа; внутри одной долгой
пары отдельного события нет.

## Офлайн-использование и JSON

`result.pairs[*].bindings` готовы сразу после `compile`/`compile_formats`.
`evaluate` не требуется и больше не входит в API матчера. Применение привязок
к значениям и предикаты реализуются вызывающим кодом.

В библиотеке нет `ArtifactReader`, версий артефактов, `from_json` или `to_json`.
Сохранение обычных данных выполняется стандартной библиотекой:

```python
import json
from dataclasses import asdict
from pathlib import Path

Path("mapping.json").write_text(
    json.dumps(asdict(result), ensure_ascii=False, indent=2),
    encoding="utf-8",
)
data = json.loads(Path("mapping.json").read_text(encoding="utf-8"))
# data["pairs"][*]["bindings"]
# data["pairs"][*]["comparison"]["relation"]
```

Результат не содержит AST или исполняемых объектов. Это обычный JSON, который
можно загрузить своим runtime-кодом. Прежние API метаданных и загрузки артефактов
удалены; сохранённые результаты старой версии следует пересчитать.

## Скрипты

```bash
python3.13 manual_format_matcher_test.py --case vlan
python3.13 manual_format_matcher_test.py --patterns device.json --documents docs.json --save mapping.json
python3.13 manual_format_matcher_test.py --patterns named.json --documents docs.json --target-syntax document --summary
```

`--mode all` включает поиск всех пересечений. `--summary` выводит только статистику.
`--save` записывает обычный JSON результата, без специального слоя хранения.

Для настоящего корпуса с массивами `CLIs` в файлах:

```bash
python3.13 benchmark_format_matcher.py --corpus /path/to/cmd_corpus --skip-invalid --report /tmp/matcher-report.json
```

Скрипт исключает `display`, сопоставляет корпус с самим собой и проверяет, что
для каждого исходного документа найдена его копия и все параметры связаны с
правильными исходными позициями. Дубли не удаляются. Некорректные форматы
перечисляются явно; без `--skip-invalid` запуск останавливается с ошибкой.
`--include-display` включает команды `display`. Чтение корпуса и запись файлов
находятся в скриптах, а не в пакете матчера.

В пакете остались `documents` (разбор форматов), `preparation` (индексы и привязки),
`comparison` (сравнение языков и исполнение структурных переходов), `models`
(результаты и состояния). Основной `vrp_parser_automaton` не изменён.
